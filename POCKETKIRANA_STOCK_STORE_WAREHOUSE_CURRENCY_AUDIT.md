## 1. Executive Summary

This audit provides a comprehensive, evidence-based analysis of the PocketKirana codebase prior to production data cleanup. The goal is to determine the exact mechanics of stock management, store and warehouse architecture, customer-facing product/catalog display, checkout reservations, picking/delivery workflows, and monetary currency handling.

### Key Audit Findings:
1. **Authoritative Stock Source**: PostgreSQL is the primary transactional authority. Live available stock is tracked across two layers:
   - Primary simplified store inventory: `inventory` table (`quantity - reserved_quantity`).
   - Detailed FEFO batch inventory: `inventory_balances` table (`available_qty` per `warehouse_id`, `variant_id`, and `batch_id`).
2. **The 39-Warehouse Root Cause (Empirically Proven)**: Querying `pocketkirana_db` revealed **39 total warehouses**, of which **37 have `store_id = NULL`**. These 37 warehouses (with codes like `WH-EXP-619229`, `WH-RACE-991880`, `WH-DRY-359856`, `WH-PERF-134107`) are synthetic test artifacts generated by automated test runner scripts (`stage_a_production_dry_run.js`, `test_expiry_clearance.js`, `phase_20_production_hardening_test.js`, `performance_load_test.js`, `e2e_order_to_delivery_test.js`) without post-test cleanup. Only **2 warehouses** are associated with actual stores (`wh_store_primary` for `store_primary` and `wh_store_central_001` for `store_central_001`).
3. **Single-Store + Single Internal Stock Location Compatibility**: The current architecture cleanly supports a **ONE STORE + ONE INTERNAL STOCK LOCATION** model. In fact, `scripts/migrate_to_clean_architecture.js` (lines 434–437) automatically provisions exactly one default darkstore warehouse (`wh_<store_id>`) for each store record (`INSERT INTO warehouses ... SELECT 'wh_' || id, id ... FROM stores`).
4. **Currency Audit**: The canonical database and payment integration APIs (PhonePe & COD) consistently use **INR (Indian Rupees / ₹)**. Invoices, delivery earnings, order totals, and checkout calculations operate strictly in INR. No active production code utilizes USD or `$`. Hardcoded currency references in external libraries (e.g. Google API client discovery cache inside pgAdmin) do not touch application runtime.
5. **Caching & Realtime Freshness**: Next.js API routes (`/api/products`, `/api/products/discover`, `/api/v1/products`) set HTTP response headers `Cache-Control: public, s-maxage=30, stale-while-revalidate=120`. While customer catalog discovery caches product lists for up to 30 seconds, **checkout stock validation executes real-time PostgreSQL row-level locks (`SELECT ... FOR UPDATE`) directly on `inventory` and `inventory_balances`**, guaranteeing zero overselling regardless of HTTP edge caching.

## 2. Current Architecture

The PocketKirana application operates under a unified hybrid model with PostgreSQL as the canonical transactional database:

```
                                  [ CUSTOMER APP / ADMIN APP ]
                                               │
                                               ▼
                              [ NEXT.JS API ROUTES / SERVER ACTIONS ]
                                               │
               ┌───────────────────────────────┴───────────────────────────────┐
               ▼                                                               ▼
  [ POSTGRESQL (pocketkirana_db) ]                            [ FIREBASE / FIRESTORE ]
  - Canonical Business Authority                              - Identity & Auth (Firebase Auth)
  - Products, Variants & Identifiers                          - Realtime Sync & Push Notifications
  - Stores, Warehouses, Inventory & Batches                   - Secondary Read Mirror (Shops/Catalog)
  - Carts, Orders, Payments, Outbox Events
  - Picking, Packing & Delivery Earnings
```

- **PostgreSQL Database**: `pocketkirana_db` on port `5433`. Holds 38 active production/operational tables across catalog, store, inventory, checkout, orders, payments, delivery, and audit modules.
- **Firebase Auth**: Manages customer and partner identity (`firebase_uid`).
- **Firestore**: Used as a secondary mirror and realtime notification engine.

## 4. Authoritative Stock Source

Here are the precise empirical answers regarding stock storage:

1. **Where is quantity initially created?**:
   - In `app/api/inventory/stock-receipt/route.ts` (updates `products.stock` & inserts row into `inventory`) and `app/api/inventory/batches/route.ts` (inserts into `inventory_batches` & `inventory_balances`).
2. **Where is quantity increased?**:
   - Stock receipt API (`/api/inventory/stock-receipt`), Batch inwarding API (`/api/inventory/batches`), or order cancellation release (`releaseFefoReservation` in [`lib/fefo.ts`](file:///d:/pocketkirana/lib/fefo.ts#L224)).
3. **Where is quantity decreased?**:
   - Reservation during checkout ([`app/api/checkout/route.ts:L237`](file:///d:/pocketkirana/app/api/checkout/route.ts#L237) decrements available balance) and picker deduction upon picking completion.
4. **Where is current available quantity calculated?**:
   - **Store Level**: `(inventory.quantity - inventory.reserved_quantity)` in [`app/api/checkout/route.ts:L226`](file:///d:/pocketkirana/app/api/checkout/route.ts#L226).
   - **Warehouse/Batch Level**: `SUM(inventory_balances.available_qty)` for active batches in [`lib/fefo.ts:L129-L138`](file:///d:/pocketkirana/lib/fefo.ts#L129-L138).
5. **Where is reserved quantity stored?**:
   - `inventory.reserved_quantity`, `inventory_balances.reserved_qty`, and active records in `stock_reservations` (`status = 'reserved'`).
6. **Where is damaged/expired/disposed quantity stored?**:
   - `inventory_balances.damaged_qty`, `inventory_balances.expired_qty`, `expiry_records`, and `stock_disposals`.
7. **Where is batch quantity stored?**:
   - `inventory_batches.received_qty` (initial received) and `inventory_balances.available_qty` (live available).
8. **Where is expiry information stored?**:
   - `inventory_batches.expiry_date` and `expiry_records.expiry_date`.
9. **Which table does customer-facing product/catalog API read?**:
   - [`app/api/products/route.ts`](file:///d:/pocketkirana/app/api/products/route.ts#L34) reads `products.stock` and `product_variants.stock_quantity`.
10. **Which table does checkout use for stock validation?**:
    - [`app/api/checkout/route.ts:L216`](file:///d:/pocketkirana/app/api/checkout/route.ts#L216) queries `inventory` and [`lib/fefo.ts:L129`](file:///d:/pocketkirana/lib/fefo.ts#L129) queries `inventory_balances` with `FOR UPDATE`.
11. **Which table does order placement use?**:
    - `orders`, `order_items`, `stock_reservations`, `inventory`, `inventory_balances`, `inventory_events`.
12. **Which table does picker use?**:
    - `picking_tasks`, `picking_task_items`, `order_items`, `product_variants.barcode`, `inventory_batches`.
13. **Which table does delivery use, if any?**:
    - `delivery_assignments`, `orders`, `order_addresses`, `delivery_partners`, `delivery_earnings`. Delivery partners do NOT read or modify stock tables directly.
14. **Which table is considered canonical by the code?**:
    - **PostgreSQL `inventory` and `inventory_balances`** tables are the canonical transactional authorities.

## 5. Admin Inventory Flow

### Scenario: Admin Inwards Stock (Product = Amul Gold Milk, Quantity = 50, Price = ₹68)

```
[ Admin UI ]
     │  POST /api/inventory/batches  OR  POST /api/inventory/stock-receipt
     ▼
[ API Handler ] ──> Validates positive quantity (0.001 precision), authenticates token
     │
     ▼
[ PostgreSQL Transaction (BEGIN) ]
     ├─► SELECT FOR UPDATE on `products` / `inventory`
     ├─► INSERT INTO `inventory_batches` (warehouse_id, variant_id, batch_number, expiry_date, received_qty=50)
     ├─► INSERT INTO `inventory_balances` (warehouse_id, variant_id, batch_id, available_qty=50, reserved_qty=0)
     ├─► INSERT INTO `inventory_transactions` (transaction_type='STOCK_RECEIPT', quantity=50)
     ├─► INSERT INTO `inventory_events` (event_type='RECEIVED', quantity=50)
     └─► UPDATE `products` SET stock = stock + 50
     │
     ▼
[ PostgreSQL Transaction (COMMIT) ] ──> Invalidates Server-Side Store Cache
```

### Constraint & Invariant Answers:
- **Can admin add stock without creating a warehouse?**: Yes, via `/api/inventory/stock-receipt` (which auto-targets `storeId`). In `/api/inventory/batches`, if `warehouseId` is omitted, the API automatically resolves the primary warehouse using `getPrimaryWarehouseIdForStore(storeId)` ([`app/api/inventory/batches/route.ts:L140`](file:///d:/pocketkirana/app/api/inventory/batches/route.ts#L140)).
- **Is warehouse_id mandatory?**: Mandatory in `inventory_batches` and `inventory_balances` tables, but auto-resolved by backend code if omitted by admin caller.
- **Is store_id mandatory?**: Mandatory in `stores` and `inventory` tables. Defaults to `'store-001'` or `'store_primary'` if omitted.
- **Is batch_id mandatory?**: Mandatory for FEFO tables (`inventory_balances`, `expiry_records`), but optional in legacy `/api/inventory/stock-receipt`.
- **Is expiry date mandatory?**: Optional. Non-perishable items (e.g. salt, detergent) set `expiry_date = NULL`.
- **Is inventory balance automatically created?**: Yes, [`app/api/inventory/batches/route.ts:L169`](file:///d:/pocketkirana/app/api/inventory/batches/route.ts#L169) automatically inserts matching `inventory_balances` record.
- **Is inventory transaction created?**: Yes, inserted into `inventory_transactions`.
- **Is inventory event created?**: Yes, logged into `inventory_events`.
- **Is cache updated?**: Store operational cache is invalidated via `clearStoreCache()`.
- **Is Firestore involved?**: Firestore is updated secondary/async if catalog mirror is enabled; PostgreSQL is the sole transactional source of truth.
- **Is PostgreSQL canonical?**: **YES, 100% CANONICAL.**

## 7. Cart → Checkout → Order Stock Flow

### Complete Stock Lifecycle (Initial Stock = 50, Customer buys 2 units):

```
1. CART ADDITION:
   Customer adds 2 units to cart.
   Stock level remains 50. (Cart does NOT reserve stock).

2. CHECKOUT SUBMISSION (POST /api/checkout):
   - Opens PostgreSQL transaction.
   - Executes: SELECT quantity, reserved_quantity FROM inventory WHERE variant_id = $1 FOR UPDATE.
   - Checks: (50 available >= 2 requested) -> PASS.
   - Updates `inventory`: SET reserved_quantity = reserved_quantity + 2.
   - Updates `inventory_balances`: SET reserved_qty = reserved_qty + 2, available_qty = available_qty - 2.
   - Inserts row in `stock_reservations` (expires_at = NOW() + 15 mins).
   - Inserts row in `inventory_events` (eventType = 'RESERVED', quantity = 2).
   - Creates order record in `orders` (order_status = 'PLACED', payment_status = 'pending').

3. PAYMENT SUCCESS:
   - Order transitions PLACED -> CONFIRMED.
   - Stock reservation status remains 'reserved' (held for picking).

4. PICKING WORKFLOW (Picker App):
   - Picker completes picking task.
   - Stock event logged: eventType = 'PICKED'.

5. DELIVERY & FINAL STOCK DEDUCTION:
   - Order marked DELIVERED.
   - `inventory.quantity` reduced from 50 to 48, `reserved_quantity` reduced from 2 to 0.
   - Final available stock in PostgreSQL: 48.
```

### Lifecycle Case Answers:
- **Does cart reserve stock?**: No.
- **Does checkout reserve stock?**: **Yes**, reserves stock in PostgreSQL for 15 minutes (`stock_reservations`).
- **Does order creation reserve stock?**: Yes, executed within the checkout atomic transaction.
- **When does actual stock decrease?**: Available stock decreases immediately at checkout reservation (`available_qty = available_qty - 2`). Total physical stock is reconciled upon picking/delivery completion.
- **When is stock reservation released?**: Released upon order completion, order cancellation, or 15-minute expiration if unpaid/abandoned.
- **What happens when order is cancelled?**: `releaseFefoReservation` in [`lib/fefo.ts`](file:///d:/pocketkirana/lib/fefo.ts#L224) returns `reserved_qty` back to `available_qty`, sets reservation status to `'released'`, and logs `RELEASED` event in `inventory_events`.
- **What happens when payment fails?**: Order remains `PLACED`/`pending`. If payment is not completed within 15 minutes, background worker calls `releaseFefoReservation`.
- **What happens when customer abandons cart?**: Cart is stored in PostgreSQL `carts` / `cart_items`. No stock is reserved until checkout submit button is pressed.
- **What happens when item is unavailable?**: Checkout returns HTTP 400 with `{ error: "Item X is out of stock (available: 0)" }` and rolls back transaction.
- **What happens when picker finds insufficient stock?**: Picker flags item status as `out_of_stock` in `picking_task_items`. Order service updates order item picked quantity, adjusts order total, logs inventory discrepancy event, and triggers customer notification/refund.
